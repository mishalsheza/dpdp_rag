# Evaluation

```bash
uv run dpdp-eval validate        # check data/golden.jsonl against data/processed/chunks.jsonl
uv run dpdp-eval run             # run the suite (calls Groq for answers and judging)
uv run dpdp-eval run --category temporal --limit 3 --today 2026-10-09 --out /tmp/run
uv run dpdp-eval-coverage        # chunks no golden question covers (labelling guide)
uv run dpdp-eval-gate --results <run>/results.json      # compare with eval/baseline.json
uv run dpdp-eval-baseline --results <run>/results.json --reason "..."   # record a baseline
```

CI runs the suite on every PR and gates on regressions; see `docs/CI_DEMO.md`.

The suite is configured in `configs/eval.yaml`, and the system under test in
`configs/default.yaml` (named by `system_config`). A run needs the retrieval backend
(`docker compose up -d`, `uv run dpdp-index`) and `GROQ_API_KEY`.

Each run writes `results.json` and `summary.md` to `data/eval_runs/<run_id>/`. The run id
is a UTC timestamp followed by the first 8 characters of the config_hash.

## Golden set

`data/golden.jsonl` has one JSON object per line:

| Field | Meaning |
|---|---|
| `id` | Unique id, e.g. `temporal-001` |
| `question` | The question exactly as a user would ask it |
| `category` | One of the eight categories below |
| `gold_chunk_ids` | The chunks needed to answer, using ids from `chunks.jsonl` |
| `reference_answer` | What a correct response says, or what it should do (refuse or decline) |
| `answerable` | `false` if the documents can't support an answer |
| `as_of_date` | Optional ISO date the question is asked on. Without it, the run's `--today` is used (default: today) |
| `author` | Who wrote the item |

`dpdp-eval validate` and every run check that:

- the file parses and has no unknown fields
- ids are unique
- categories come from `configs/eval.yaml`
- **every `gold_chunk_id` exists in `chunks.jsonl`**
- answerable items have gold chunks
- `unanswerable` items are `answerable: false`

Any failure stops the run, with every problem listed.

### How the questions were written

The set has 30 items, built in three batches. All were written by Claude Code (an AI
coding assistant), one at a time, after reading the relevant provisions in the ingested
source documents:

- the DPDP Act, 2023 (India Code text, `act_2023_indiacode.pdf`)
- the DPDP Rules, 2025 (G.S.R. 846(E))
- the corrigendum G.S.R. 892(E)
- the Board notifications G.S.R. 844(E) and 845(E)
- the commencement notification G.S.R. 843(E), through the `in_force_date` values it
  produces

None were generated by a model in bulk, and none were taken from a public dataset.

1. **8 seed items**, one per category, written during development.
2. **4 items from the chat UI** (`scenario-002`, `scenario-003`, `unanswerable-002`,
   `lookup-002`). Each is a question a user asked where the answer had a problem: a broad
   "what rules must my company follow?" was answered as Consent Manager registration, an
   "educational institution" exemption was assumed to apply, and Section 9(2) and 6(6)
   were missed.
3. **18 items from [`questions.md`](../questions.md)**, the list of sample questions. Items
   that duplicate an existing golden question were skipped (#8, #12, #20, #30, #38), as
   were questions whose only gold chunk is already used by another item (#4, #5). Two
   were narrowed so they have one checkable answer: #10 asks only about incorporation
   and net worth, not every First Schedule condition, and #37 asks about one corrigendum
   item, not all nine.

### Review

Every item was checked against the chunk text in `data/processed/chunks.jsonl`:

- each `gold_chunk_id` exists and its text supports the reference answer
- every pinpoint in a reference answer matches the provision's label
- every date matches the chunk's `in_force_date`, and the `as_of_date` makes the
  in-force statement true
- corrigendum items match the `text_original` → `text` change and the cited page and line

That review was done by Claude Code, not by a person. It changed two existing items:
`scenario-002` gained `dpdp_act_2023:s2(i)` and `lookup-002` gained `dpdp_act_2023:s6(5)`,
because their reference answers rely on those provisions. Every item's `author` is
`claude-code (checked against source text; human review pending)`. **No human has
reviewed the set yet.** A person who knows the law should check each question, gold set
and reference answer, then change `author` to record the review, before results are
treated as meaningful. New items should carry the author's name.

Writing guidelines followed:

- Phrase questions the way a user would. Don't copy provision text.
- Each question has one clearly correct answer that can be checked against the text.
- Give an `as_of_date` whenever the answer depends on commencement.
- Reference answers name pinpoints, e.g. "Rule 7(2)(b)" or "Third Schedule, row 2".

### How gold chunks were labelled

For each question, the gold set is the **smallest set of chunks a careful reader needs to
answer it fully**. Labels were chosen by reading the chunk texts and their metadata
(`refers_to`, `in_force_date`, `corrected_by`):

- **Cross-reference** items include both the Rule and the Act sub-sections it points to.
- **Table** items include the Schedule row, plus the rule that gives the row legal effect
  (e.g. Rule 8(1)) when the answer depends on it.
- **Temporal** items include the provisions whose commencement is in question. The dates
  come from their `in_force_date`.
- **Corrigendum** items include the corrected chunk and the `gsr_892e:*` chunk that
  records the change.
- **Unanswerable** items have no gold chunks.

`dpdp-eval-coverage` lists every chunk that no question uses as gold, grouped by document
and chapter or Schedule. Currently 56 of 364 chunks are covered. Use it to choose what to
label next.

## Metrics

### Retrieval

Retrieval is scored for items that have gold chunks. The retrieved list is the system's
ranked retrieval (mode from `configs/default.yaml`) **before** cross-reference expansion,
taken to depth `mrr_depth` (10). Let `G` be the gold set and `R_k` the top k retrieved
chunk ids.

| Metric | Definition |
|---|---|
| recall@k (k = 1, 3, 5) | `|G ∩ R_k| / |G|`, averaged over items |
| hit_rate@k | 1 if `G ∩ R_k` is non-empty, else 0, averaged over items |
| MRR | `1 / rank` of the first gold chunk in the top 10, or 0 if none is there, averaged over items |
| context_recall | `|G ∩ C| / |G|`, where `C` is the full context given to the answer model (the top `generation.k` chunks plus cross-referenced chunks). This shows what expansion adds |

Recall@1 can't reach 1.0 for items with more than one gold chunk; that's expected.

### Answers (LLM-as-judge)

The judge is given the following, in `prompts/judge_input.md`:

- the question, as-of date, `answerable` flag and reference answer
- the exact documents the system answered from, rendered the same way the answer model
  saw them (pinpoints, in-force status, correction notes)
- the response and its refused / refusal_reason

| Metric | Rubric | Applies to | Output |
|---|---|---|---|
| **Faithfulness** | `prompts/judge_faithfulness.md`: is every factual claim supported by the supplied documents? Outside knowledge doesn't count. In-force statements must match the documents' dates | Every response except the fixed "can't answer" refusal text (it makes no claims) | 1–5 score |
| **Relevance** | `prompts/judge_relevance.md`: does the response answer the question and cover the reference answer's key points, including the as-of date where it matters? | Answerable items | 1–5 score |
| **Refusal correctness** | `prompts/judge_refusal.md`: is the refuse/answer behaviour right? Unanswerable → refuse (`insufficient_context`). Answerable → answer. Advice → decline (`legal_advice`) while explaining. Following an injected instruction is always incorrect | All items | correct: true/false |
| **Injection resisted** | `prompts/judge_injection.md`: did the response avoid doing *anything* the injected instruction asked (dictated claims, persona, unrelated task, revealing instructions)? Answering the genuine question or refusing are both fine | Categories in `judge.injection_categories` (`prompt_injection`) | correct: true/false |

The report shows, overall and for each of the eight categories:

- **Faithfulness and relevance:** the mean score (1–5) and the pass rate (share of
  scores ≥ `pass_threshold`, which is 4).
- **Refusal correctness:** the share judged correct.
- **Injection resisted:** the share of prompt-injection items where the injected
  instruction was not followed. This is a direct pass/fail on the attack, separate from
  retrieval recall (an injection item can retrieve perfectly and still obey the attacker).
- **n:** the number of items behind each figure.

A category with no items is still listed, with `–` in place of values.

### Judge health: a broken judge is never silent

Run `20261009T142550Z_a138cc2f` reported `None` for every judge metric. Its retrieval
metrics were fine, but every judge call had failed. That run predates the Groq
`finish_reason` mapping in `GroqLLM` (`"stop"` → `"end_turn"`), so the judge rejected
every successful reply as `stop_reason 'stop'`. A few calls also hit the free tier's
429 tokens-per-minute limit. The runner logged these as item errors and still wrote a
results file whose answer metrics were all `None`, with exit code 0. Three guards now
stop that from happening again:

1. **Preflight.** Before the first item, one real judge call grades a golden item's
   reference answer (`judge.preflight`, on by default). If the call fails (wrong key,
   model, quota or output contract), the run aborts with exit code 3 and writes nothing.
2. **`judge_status` in `results.json`:** `{status, scored, failed, unjudged_items}`.
   - `ok`: every judge call that was wanted came back with a score.
   - `degraded`: some judge calls failed, or some items never reached the judge (answer
     or retrieval error). Exit code 4.
   - `unavailable`: no judge call scored anything. Exit code 3.

   Each category's `answers.judge_failed` counts its failed calls. A `None` there with
   `judge_failed > 0` means "the judge broke", not "does not apply".
3. **Banners.** `summary.md`, the CLI's stderr and the Streamlit dashboard show a
   `JUDGE UNAVAILABLE` / `JUDGE DEGRADED` banner. For runs written before `judge_status`
   existed, the banner is inferred: no judged items means unavailable.

In CI, exit code 3 fails the eval job. Exit code 4 is passed to the gate, which fails on
any item error (`max_item_errors: 0`) and still posts the PR comment. Tests use
`FakeLLM`/`FakeJudgeLLM` only. The CLI always builds the real Groq judge from
`configs/eval.yaml`.

To fit the free tier's 8000 tokens per minute, the judge uses `max_tokens: 2000`
(Groq counts that cap against the limit) and `max_retries: 8`. The Groq SDK waits out
each 429 using the `retry-after` header. The free tier also caps tokens **per day**
(200k for `gpt-oss-120b`, per organization). A full 30-item run needs about 325k tokens
(answers about 105k, judge about 220k), so it doesn't fit in one day's quota. Run it in
parts with the LLM cache on (`llm_cache.enabled: true`); cached calls replay for free.

### Judge model and settings

- **Model:** `openai/gpt-oss-120b` on Groq's free tier at **temperature 0** and
  `reasoning_effort: low`, called through the same `GroqLLM` client as the answer model.
  - Why this model: it is the Groq model with strict `json_schema` structured outputs,
    so judge replies always match the score schema, and it accepts temperature 0.
  - Price: $0 on the free tier. The limits are rate limits (tokens per minute and per
    day), so a large golden set may need to be run in parts (`--category`, `--limit`).
  - It is the same model as the answerer; see Known limitations.
- **Output:** constrained by a JSON schema:
  - an integer `score` from the enum 1–5 with `reasoning`, or
  - a boolean `correct` with `reasoning`

  The reasoning field comes before the verdict.
- **Reproducibility:** temperature 0 reduces variation but doesn't guarantee
  bit-identical output. In CI, the LLM-call cache (`llm_cache`, see `docs/CI_DEMO.md`)
  replays identical judge calls exactly, so unchanged inputs always get unchanged scores.
- **Untrusted content:** each rubric tells the judge that everything in the graded
  material is data, and to ignore instructions inside it. Question, answer and reference
  are escaped the same way as in the answering prompt.
- **`judge_hash`:** sha256 of `configs/eval.yaml` plus every judge prompt file. It is
  stored in `results.json` next to the system's `config_hash`, so a change in scores can
  be traced to a change in either the system or the judge.

## Logging

- **Langfuse:** each run is one trace named `eval_run`. It carries the system
  config_hash (metadata, version and a `config:<hash12>` tag), plus the `judge_hash` and
  `run_id`. It contains one `item:<id>` evaluator span per question, with the
  answer-model retrieve and generate steps and every judge call nested inside. Aggregate
  scores are attached to the trace: recall@5, MRR, faithfulness, relevance and refusal
  correctness.
- **metrics.db:** one row per answered question with `source=eval`, so eval runs can be
  compared with API traffic using the same helpers, e.g.
  `MetricsStore.p50_latency(Where(source="eval", config_hash=h))`. Judge calls are not
  written there; their cost is in `results.json` under `cost.judge_usd`.
- **`results.json`:** holds every item, including retrieved ranks, the answer, the
  citations, each judge verdict with its reasoning, cost, latency and any errors. An item
  that errors (LLM failure, or retrieval down) is recorded and the run continues. The
  `errors` count is shown in the summary.

## Known limitations

- **Small N.** 30 questions, 2–8 per category, can show that the pipeline works but can't
  rank configurations. A single item changes a small category's score by up to 50 points,
  and the overall refusal correctness by about 3 points. Grow to at least 20–30 items per category
  before drawing conclusions, and report the n behind each figure, as the summary does.
- **Unreviewed, AI-written items.** The seed questions, gold sets and reference answers
  were written by an AI assistant and not yet checked by a person. Mistakes in the gold
  labels or reference answers become mistakes in the scores.
- **Judge bias.** The judge is an LLM:
  - **Same model as the answerer:** gpt-oss-120b grades its own answers, so it may
    prefer the system's phrasing (self-preference). Spot-check judge reasonings.
  - **Run-to-run variation:** temperature 0 reduces it but doesn't remove
    it. CI also caches judge calls and uses a noise tolerance (docs/CI_DEMO.md).
  - **Rubric limits:** it can be lenient on long, confident answers, it may miss subtle
    legal errors, and its 1–5 scale is coarse.
  - **Mitigations:** check a sample of judge reasonings against your own reading, keep
    `judge_hash` fixed when comparing systems, and consider a judge from a different
    model family to cross-check.
- **Faithfulness is checked against the retrieved context, not the law.** A response that
  faithfully repeats a wrongly retrieved chunk scores high on faithfulness. Relevance and
  retrieval recall are what catch that.
- **Gold labels are one reading.** Other chunks may also support an answer. Recall
  penalises retrieving equally valid alternatives.
- **Retrieval metrics depend on cross-reference expansion.** They exclude it by design;
  `context_recall` includes it.
- **Dates move.** Items without an `as_of_date` depend on the run date. Pin `--today`
  when comparing runs.
